## 第 5 章：扩展 Pi 的三种方式

Pi 把"扩展能力"拆成了三种颗粒度不同的机制，分工非常清晰：

| 机制 | 解决什么问题 | 本质 |
|---|---|---|
| **Prompt Templates** | 把常用的一段话存成模板，避免重复打字 | 一个 `.md` 文件，`/文件名` 触发 |
| **Skills** | 给模型"按需加载"的专业知识/操作手册 | 一个带 `SKILL.md` 的目录，模型自己判断何时读取 |
| **Extensions** | 真正改变 Pi 的行为：新工具、新命令、拦截事件 | 一个 TypeScript 模块，跑在 Node 里，能力最强 |

**为什么不只留一种？** 你可能会想：Extension 最强，全用 Extension 不就好了？这里有个重要的权衡——**越靠下的机制能力越强，但成本也越高**：Extension 是跑在 Node 里的代码，写错会真的搞坏你的系统；而 Prompt Template 只是个 `.md` 文件，写错了顶多是模型回错话。所以 Pi 的建议是**从上往下选**：能用模板解决的别用 Skill，能用 Skill 解决的别写 Extension。只有在“必须给模型新增一个能调用的动作”时才动用 Extension——本教程第 6 章的多角色团队就属于这一种。

按“复杂度递增”的顺序，我们一个个看。

### 5.1 Prompt Templates：最简单的复用

新建 `.pi/prompts/review.md`：

```markdown
---
description: 审查当前 staged 的改动
argument-hint: "[关注点]"
---
审查 `git diff --cached` 里的改动，重点关注：
- Bug 和逻辑错误
- 安全问题
- 错误处理是否完整

额外关注点：${1:-无}
```

用法：`/review` 或 `/review 性能`。变量语法：

- `$1`、`$2` ……：按位置取参数
- `$@` / `$ARGUMENTS`：全部参数
- `${1:-默认值}`：没传参数时用默认值

存放位置：全局 `~/.pi/agent/prompts/*.md`，项目 `.pi/prompts/*.md`（项目需先被信任）。**注意不递归子目录**，子目录模板要在 settings 里显式声明。

### 5.2 Skills：按需加载的"说明书"

Skill 是一个目录，里面至少有一个 `SKILL.md`：

```
my-skill/
├── SKILL.md
├── scripts/process.sh
└── references/api-reference.md
```

`SKILL.md` 格式：

```markdown
---
name: pdf-processing
description: 从 PDF 中提取文本和表格。当用户要求处理/解析 PDF 文件时使用。
---

# PDF 处理

## 用法
./scripts/process.sh <输入文件>
```

**关键机制是"渐进式披露"**：Pi 启动时只把每个 Skill 的 `name`/`description` 塞进系统提示词，模型觉得任务匹配时才会去读完整的 `SKILL.md` 正文。这样即使你装了几十个 Skill，也不会把上下文塞爆。

也可以强制调用：`/skill:pdf-processing 提取表格`。

放置位置：全局 `~/.pi/agent/skills/`，项目 `.pi/skills/`。

**Skill 和 Extension 怎么选？** 简单判断：如果你只是想给模型"一份操作指南"（哪怕带几个辅助脚本），用 Skill；如果你要让 Pi **本身多一个能力**（新工具、拦截某个事件、加命令），用 Extension。本教程后面搭建的"多角色团队"，因为需要真正新增一个 `delegate` 工具，所以必须用 Extension。

### 5.3 Extensions：真正的编程扩展

Extension 是一个 TypeScript 文件（或目录），导出一个默认函数，接收 `ExtensionAPI`：

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("session_start", async (_event, ctx) => {
    ctx.ui.notify("扩展已加载！", "info");
  });
}
```

存放位置和 Skills 类似：全局 `~/.pi/agent/extensions/*.ts`，项目 `.pi/extensions/*.ts`（或对应的目录形式 `.../index.ts`）。项目里的扩展**只有项目被信任后才会加载**——这是合理的安全边界，因为"扩展以你的全部系统权限运行"。

**先认清两个会反复出现的核心对象**——上面这段 6 行代码里已经把它们都用上了，后面整章、乃至第 6 章的所有扩展代码都建立在这两个对象之上：

- **`pi`（类型 `ExtensionAPI`）** — 你的扩展和 Pi 框架之间的"接线柱"。框架加载你的扩展时会调用你导出的这个默认函数，把 `pi` 传进来；你扩展能做的一切——注册工具、注册命令、监听事件、写会话记录——都是**调用 `pi` 上的方法**完成的。可以把它理解成"Pi 给你的一把操作把手"：`pi.registerTool(...)` 加工具、`pi.registerCommand(...)` 加命令、`pi.on(...)` 挂事件、`pi.appendEntry(...)` 写会话状态。这段例子里用的 `pi.on("session_start", ...)` 就是"会话启动时跑一段我的代码"。

- **`ctx`（类型 `ExtensionContext`）** — 每次被调用时的"现场环境"。跟 `pi` 不同：`pi` 在整个扩展生命周期里是同一个，`ctx` 是**每次事件触发时新生成**的，里面装着这次调用能拿到的东西——`ctx.cwd`（当前工作目录）、`ctx.ui`（弹通知、弹确认框的界面接口）、`ctx.sessionManager`（读写会话历史）、`ctx.hasUI`（当前是不是交互模式）。这里用 `ctx.ui.notify(...)` 推了一条通知到 Pi 的界面。

一句话区分：**`pi` 用来"注册"（启动时配好），`ctx` 用来"干活"（每次事件触发时拿现场信息）**。

Extension 能做三件事，我们逐个看：

#### (a) 注册工具（`pi.registerTool`）

这是最重要的能力——给模型新增一个可以调用的动作：

```typescript
import { Type } from "typebox";

pi.registerTool({
  name: "greet",
  label: "Greet",
  description: "跟某人打招呼",
  parameters: Type.Object({
    name: Type.String({ description: "对方的名字" }),
  }),
  async execute(toolCallId, params, signal, onUpdate, ctx) {
    return {
      content: [{ type: "text", text: `你好，${params.name}！` }],
      details: {},
    };
  },
});
```

几个要点：

- `parameters` 用 [typebox](https://github.com/sinclairzx81/typebox) 定义 JSON Schema。
- 如果需要“枚举”类型的参数，用 Pi 提供的 `StringEnum(["a", "b"] as const)`，**别用** typebox 原生的 `Type.Union`/`Type.Literal`——文档特别提到这两个在 Google 的 API 上不工作。
- `execute` 里 `throw` 才算失败，`return` 一个值永远不会被标记为出错。
- 想中途报告进度，用 `onUpdate?.(...)`。

**`execute` 的五个参数分别是什么**（这个签名后面每个扩展都会出现，先认清一次）：

- `toolCallId` — 本次调用的唯一 id，一般用不到，通常写成 `_toolCallId` 表示"故意不用"。
- `params` — 模型按 `parameters` 里的 schema 传进来的参数对象，也就是这里的 `{ name }`。
- `signal` — 一个 `AbortSignal`，上层一旦取消（用户按了停止），它会触发；跑长任务时要监听它及时收手（第 6 章会用到）。
- `onUpdate` — 上面提到的进度推送函数，`?.` 表示它可能不存在，所以要用可选调用。
- `ctx` — 上下文对象，工具运行时能拿到的一切都挂在它上面：`ctx.cwd`（当前目录）、`ctx.ui`（弹通知/确认框）、`ctx.sessionManager`（读写会话）等。

**返回值为什么长这样**（`{ content, details }`）：

- `content` 是**给模型看的结果**——它会作为一条工具结果消息喂回对话，所以要放模型需要的信息（这里是打招呼的文字）。
- `details` 是**给程序/界面看的结构化附加数据**，不进模型上下文，常用来放日志、状态、原始对象，方便调试或自定义 UI 渲染。这条"模型看 `content`、程序看 `details`"的分工在第 6 章会反复用到。

**模型怎么知道“什么时候该用这个工具”？** 你调过 function calling，知道靠的是工具的 `description`——模型就是看它来决定要不要调。Pi 在此之上还多了两个字段：`promptSnippet` 是塞进系统提示词的一句工具简介（让模型知道有这个工具），`promptGuidelines` 是一组“该怎么用”的使用守则（比如“每次只派一个角色”）。合起来就是三层：`description` 管“要不要调”，`parameters` 管“怎么传参”，`promptGuidelines` 管“按什么策略调”。第 6 章的 `delegate` 工具会把这三层都用上。

#### (b) 注册命令（`pi.registerCommand`）

```typescript
pi.registerCommand("stats", {
  description: "显示当前会话统计",
  handler: async (args, ctx) => {
    const count = ctx.sessionManager.getEntries().length;
    ctx.ui.notify(`当前会话有 ${count} 条记录`, "info");
  },
});
```

这段做的事很简单：注册一个叫 `stats` 的命令，用户敲 `/stats` 时就执行 `handler`。`handler` 里 `ctx.sessionManager.getEntries()` 取出当前会话的所有记录（每条用户发言、每次模型回复、每次工具调用都算一条"记录"），`.length` 就是它的条数，再用 `ctx.ui.notify` 弹一条通知显示出来。

- `args` 是命令后面跟的参数，比如 `/stats foo` 里的 `foo`（这里没用到）。
- `ctx` 跟工具的 `ctx` 是同一类东西——命令能拿到的会话、界面等都挂在它上面。

这就是 `/stats` 这种斜杠命令的来源。我们后面的 `/team` 命令也是这么做的。

#### (c) 监听/拦截事件（`pi.on`）

事件是 Extension 里最"高阶"的能力，可以在关键节点插入逻辑，甚至**拦截并阻止某个工具调用**：

```typescript
pi.on("tool_call", async (event, ctx) => {
  if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
    const ok = await ctx.ui.confirm("危险操作！", "确定要执行 rm -rf 吗？");
    if (!ok) return { block: true, reason: "被用户拦截" };
  }
});
```

这里新出现一个核心对象 **`event`**——它描述"这次事件发生了什么"。不同事件携带的 `event` 形状不同：`tool_call` 事件里，`event.toolName` 是要调用的工具名（`bash`/`read`/`write`…），`event.input` 是模型传给这个工具的参数对象（对 `bash` 来说就是 `{ command: "..." }`）。你的拦截逻辑就是读这两个字段做判断：是不是 `bash`？命令里有没有 `rm -rf`？命中就 `ctx.ui.confirm` 弹确认框，用户拒绝就返回 `{ block: true, reason }`——`block: true` 阻止工具执行，`reason` 会作为工具结果回给模型（模型据此知道"被拦了"再决定下一步）。不 return 或 return `undefined` 就表示放行。

> 不同事件的 `event` 字段不一样（比如 `session_start` 的事件几乎没字段、`agent_end` 带 token 用量）。记不住没关系——用到时查 SDK 文档对应的事件类型即可。

Agent Loop 的完整事件时间线，画成嵌套树状（缩进代表“谁包着谁”）：

```
project_trust          ← 项目被信任，一次性
  └─ session_start     ← 每次开会话：加载扩展、上下文
       └─ resources_discover
            └─ input          ← 你发一句话
                 └─ before_agent_start
                      └─ agent_start    ← 一次“开始思考”
                           └─ turn_start ← 一轮（一次思考里可能多轮）
                                ├─ context
                                ├─ tool_call → tool_result（可能多次）
                                └─ turn_end
                           └─ agent_end   ← 这次思考结束
                 └─ agent_settled
```

看出嵌套关系很重要：一次 session 里可能有多次 `agent_start`（你说一句、模型干一轮，再说一句又干一轮），一次 `agent_start` 里可能有多轮 `turn`（模型连续调好几个工具），一轮 `turn` 里可能有多次 `tool_call`。挂事件时按这个层级选——想“每次 Agent 说完话就做点什么”挂在最外层的 `agent_end`；想“每次工具调用前检查一下”挂在 `tool_call`；想拦在最外层“会话刚启动”用 `session_start`（本教程的加载通知就挂这里）。

### 5.4 Pi Packages：打包分发

当你的扩展/Skill/模板攒多了，想分享给团队或发到 npm，就用 Pi Package——本质是一个多加了 `pi` 字段的 `package.json`：

```json
{
  "name": "my-pi-package",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./extensions"],
    "skills": ["./skills"],
    "prompts": ["./prompts"]
  }
}
```

别人安装：

```bash
pi install npm:@org/my-pi-package@1.0.0
pi install git:github.com/user/repo@v1
pi install /本地/路径
```

我们本教程的示例项目本身就会长成这个样子。
