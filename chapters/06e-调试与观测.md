## 第 6e 章：调试与观测

> **本章定位**：你已经能跑起来多角色团队，但某个角色行为不对时，你要去哪里看？本章回答这个问题——Pi 给你提供了哪些观测手段，怎么在不跑完整 `/team` 流程的前提下定位问题。

### 6e.1 Pi 内置的可见性

先从最简单的开始：你不需要加任何代码，Pi 的 UI 就已经在替你记录很多东西了。

每次工具调用，Pi 默认在界面上显示**工具名、传入参数、返回结果**。对于 `delegate` 这类调用，你能直接看到 Leader 派了什么任务给哪个角色、那个角色返回了什么。这是你的第一层观测窗口——在加任何调试代码之前，先把这层看完。

两个主动观测的基础原语：

**`ctx.ui.notify()`** 把一条通知推到 Pi 的界面，不打断对话流。适合状态通报，比如"coder 开始处理第 2 次返工"。

**`onUpdate?.()`** 是工具 `execute` 里的进度推送接口，在工具还没返回时就能向上层推中间状态。多角色扩展里已经用了它：

```typescript
onUpdate?.({ content: [{ type: "text", text: `[${role}] 开始处理...` }] });
```

这一行会在子 Agent 跑起来之前就在界面上出现，让你知道 delegate 到底触发了没有。你可以在熔断检查之后、子会话创建之前，加一条更详细的通知：

```typescript
onUpdate?.({
  content: [{
    type: "text",
    text: `[${role}] 第 ${coderDelegationCount}/${MAX_CODER_DELEGATIONS} 次派单，任务长度 ${params.task.length} 字`
  }]
});
```

### 6e.2 用事件 API 观测 Leader 的行为

`pi.on()` 不只能用来拦截，也能纯粹用来观测。在扩展里挂一个调试监听器，记录 Leader 的每次工具调用，不改任何业务逻辑：

```typescript
// 只在开发时用——生产环境把这一段删掉或用环境变量 gate 住
if (process.env.PI_DEBUG) {
  pi.on("tool_call", async (event, _ctx) => {
    console.error(
      `[tool_call] ${event.toolName}`,
      JSON.stringify(event.input, null, 2)
    );
  });

  pi.on("agent_end", async (_event, _ctx) => {
    console.error("[agent_end] Leader 本轮结束");
  });
}
```

注意用 `console.error` 而不是 `console.log`——Pi 通常把 stderr 单独处理，不会和模型的正常对话混在一起，更容易找。

事件挂哪里，取决于你想观测什么：

| 想看什么 | 挂哪个事件 |
|---------|-----------|
| Leader 调了哪些工具、传了什么参数 | `tool_call` |
| 每轮工具调用结束后的完整结果 | `turn_end` |
| Leader 说完一段话的节点 | `agent_end` |
| 整个 `/team` 命令结束时做清理/统计 | `agent_settled` |

### 6e.3 观测子 Agent 的内部

这是最容易被忽略的盲区。`delegate` 工具拿到的只是子 Agent 的最终文字输出，但你有时需要知道：Reviewer 到底调了哪些工具？Coder 跑了什么命令？

进入子 Agent 内部的唯一窗口是 `session.subscribe()`。当前示例里它只收集了文字：

```typescript
const unsubscribe = session.subscribe((event) => {
  if (
    event.type === "message_update" &&
    event.assistantMessageEvent.type === "text_delta"
  ) {
    output += event.assistantMessageEvent.delta;
  }
});
```

扩展一下，同时记录工具调用：

```typescript
const toolLog: string[] = [];

const unsubscribe = session.subscribe((event) => {
  if (event.type === "message_update") {
    const e = event.assistantMessageEvent;
    if (e.type === "text_delta") {
      output += e.delta;
    } else if (e.type === "tool_use_start") {
      toolLog.push(`→ ${e.toolName}(${JSON.stringify(e.input ?? {})})`);
    } else if (e.type === "tool_result") {
      toolLog.push(`← result (${String(e.content ?? "").length} chars)`);
    }
  }
});
```

然后在返回结果里带上工具日志（开发期间可以放进 `details`，不影响 Leader 看到的文字内容）：

```typescript
return {
  content: [{ type: "text", text: output }],
  details: { role, toolLog },
};
```

这样你就能回答"Reviewer 到底读了哪些文件、最后是不是真的调了 submit_review"——不用靠猜。

> **事件字段名的确认方法**：上面用到的 `tool_use_start`、`tool_result` 等子类型字段名，在 Pi SDK 版本迭代中可能有调整。如果改完后字段没命中，在 `subscribe` 回调里先 `console.error(JSON.stringify(event))` 打印一条原始事件，对着实际结构核对字段名，再改回来。

### 6e.4 隔离单个角色测试

跑完整 `/team` 来验证一个角色的 system prompt，每次要等 PM、Coder 都跑完才能看到 Reviewer 的行为，既慢又干扰太多。更好的做法是把单个角色抽出来单独跑。

**方法一：`pi -p`（非交互模式）**

在已信任的项目目录里：

```bash
pi -p "你是代码审查员。以下是要审查的代码：[粘贴代码]。检查完后调用 submit_review 工具提交结论。"
```

`-p` 参数让 Pi 跑完一轮就退出，适合快速验证单个角色的 prompt 和工具行为。

**方法二：写一个独立的测试脚本**

不依赖 Pi CLI，直接用 SDK 写一个小脚本，针对某个角色跑一次会话：

```typescript
// scripts/test-reviewer.ts
import {
  createAgentSession,
  ModelRuntime,
  SessionManager,
} from "@earendil-works/pi-coding-agent";
import { StringEnum } from "@earendil-works/pi-ai";
import { Type } from "typebox";

// 把 ROLES.reviewer.prompt 粘贴到这里
const REVIEWER_PROMPT = `你是团队里的代码审查员（Reviewer）。
你会收到 PM 的验收标准和 Coder 的实现结果。
只读代码，不要修改任何文件。
对照验收标准逐条检查，找出问题（bug、遗漏、风格问题）。
检查完成后，你必须调用 submit_review 工具来提交你的最终结论，
这是唯一有效的交付方式——不要只用文字描述结论而不调用工具。
verdict 填 approved 表示全部通过，填 rejected 表示不通过；
comments 里写清楚具体问题，越具体越好（比如指出文件名和大致位置）。`;

async function main() {
  const modelRuntime = await ModelRuntime.create();

  let capturedVerdict: { verdict: string; comments: string } | null = null;

  const { session } = await createAgentSession({
    cwd: process.cwd(),
    sessionManager: SessionManager.inMemory(),
    modelRuntime,
    tools: ["read", "grep", "find", "ls", "submit_review"],
    customTools: [
      {
        name: "submit_review",
        label: "Submit review",
        description: "提交审查结论",
        parameters: Type.Object({
          verdict: StringEnum(["approved", "rejected"] as const),
          comments: Type.String(),
        }),
        async execute(
          _id: string,
          params: { verdict: "approved" | "rejected"; comments: string }
        ) {
          capturedVerdict = params;
          return { content: [{ type: "text", text: "已记录" }], details: {} };
        },
      },
    ],
    systemPromptOverride: () => REVIEWER_PROMPT,
    appendSystemPromptOverride: () => [],
  });

  let output = "";
  const unsub = session.subscribe((event) => {
    if (
      event.type === "message_update" &&
      event.assistantMessageEvent.type === "text_delta"
    ) {
      process.stdout.write(event.assistantMessageEvent.delta);
      output += event.assistantMessageEvent.delta;
    }
  });

  const task = `
验收标准：
1. add(a, b) 函数存在
2. 有对应的测试

Coder 的实现总结：已在 src/math.ts 新增 add 函数，在 tests/math.test.ts 新增测试。

请审查。
  `;

  await session.prompt(task);
  unsub?.();
  session.dispose();

  console.log("\n\n--- 捕获到的结构化结论 ---");
  console.log(capturedVerdict ?? "警告：Reviewer 没有调用 submit_review");
}

main().catch(console.error);
```

运行：

```bash
node --experimental-strip-types scripts/test-reviewer.ts
```

这个脚本让你用 10 秒而不是 2 分钟验证 Reviewer 的行为，也不会动任何真实文件。本质上和第 6d 章的 CI 审查脚本是同一个模式——**把 Pi 当一个可编程组件，在它外面写测试驱动代码**。

### 6e.5 常见失败的诊断路径

遇到问题，先**确认问题是什么**，再决定改代码还是改 prompt。

**扩展没有加载**

症状：`/team` 命令不存在，或 `session_start` 的通知没出现。

1. 项目是否被信任？`/trust` 之后是否重启或 `/reload` 了？
2. 扩展文件路径是否正确？Pi 要求放在 `.pi/extensions/<name>/index.ts`（目录形式）或 `.pi/extensions/<name>.ts`（单文件形式）。
3. TypeScript 有语法错误时 Pi 会静默失败，不会显示报错。用 AGENTS.md 里提到的 stub 方式跑一次 `tsc --noEmit` 排除语法问题。

**Leader 没有调用 `delegate` 工具**

症状：Leader 直接给出了文字回答，没有走多角色流程。

挂一个 `tool_call` 事件监听看 Leader 实际调了哪些工具。如果完全没有工具调用，说明模型决定直接回答——这是 prompt 层面的问题。在 `promptGuidelines` 里加一句"必须先调用 delegate 派给 PM，不要直接回答需求"。

**Reviewer 完成了但 `delegate` 返回 `REVIEWER_DID_NOT_SUBMIT`**

说明 Reviewer 的会话跑完了但没有调用 `submit_review`。用 6e.3 里的工具日志看 Reviewer 实际调了什么——最常见的情况是它把结论写在文字里、调了 `read` 之后直接结束了，没走到 `submit_review`。

修法优先级：先加强 system prompt 里"必须调用 submit_review，这是唯一有效的交付方式"的措辞；如果还是偶尔不调，在 `promptGuidelines` 里也加一条"reviewer 完成检查后，最后一步必须是调用 submit_review，不调用则视为未完成"。

**子 Agent 持续超时或跑得很慢**

先确认 `sharedModelRuntimePromise` 真的复用了——如果每次 `delegate` 都看到模型初始化的延迟，说明缓存没生效，检查模块作用域的变量有没有被意外重置（比如 Extension 的 factory function 被多次调用）。

其次确认 Coder 的 system prompt 没有意外触发高成本推理模式——对简单任务降低推理深度，比优化缓存更有效。

### 6e.6 观测 token 消耗

多角色系统每轮 `/team` 的 token 消耗大约是单次会话的 3–5 倍（PM + Coder + Reviewer 各一个独立上下文，每个都要传入完整的 system prompt 和任务历史）。当你发现某次跑了特别久或费用异常，需要知道是哪个角色"超标"了。

一个简单的计量钩子，挂在 `agent_end` 事件上：

```typescript
if (process.env.PI_DEBUG) {
  pi.on("agent_end", async (event, _ctx) => {
    if ("usage" in event && event.usage) {
      console.error(
        `[usage] input=${event.usage.inputTokens} output=${event.usage.outputTokens}`
      );
    }
  });
}
```

具体字段名取决于 Pi SDK 版本——如果 `event.usage` 不存在，先把 `event` 完整打印出来对着看结构，再调整字段名。

### 本章小结

观测手段按深度排列：

```
Pi UI（工具调用天然可见）
  └─ ctx.ui.notify / onUpdate（主动推通知）
       └─ pi.on("tool_call" / "turn_end")（观测 Leader）
            └─ session.subscribe()（观测子 Agent 内部）
                 └─ 独立测试脚本（隔离单角色，最快速）
```

排查问题的顺序是从外到内：先看 Pi UI 里工具调用有没有触发，再看工具的 `onUpdate` 有没有推出来，再看 `subscribe` 里子 Agent 发生了什么。大多数问题在第一层或第二层就能定位，不需要走到最深处。
